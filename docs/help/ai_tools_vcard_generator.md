# VCF 名片生成器 - 帮助与学习文档

--------------------------------

## 【一】这个网页解决了什么问题？

**使用场景：**
想象一下，你参加了一场行业会议，收到了十几张纸质名片；或者你收到了一封工作邮件，对方的签名档里包含了联系方式；又或者你需要把一份手写的通讯录整理成电子版。手动一个个输入到手机通讯录里，既耗时又容易出错。

这个网页就是为解决这类问题而生的。它允许你将包含联系人信息的**任意格式文本**（如名片照片OCR后的文字、邮件签名、会议名单等）粘贴进来，然后利用AI自动识别并提取出姓名、电话、邮箱、公司、职位等信息，最后生成标准的VCF电子名片文件。你可以一键将这些文件导入到iPhone、Android手机或Google通讯录中。

**适合什么情况？**
- 批量整理纸质名片或手写通讯录。
- 快速从邮件、聊天记录、文档中提取联系人信息。
- 需要将非结构化的联系人文本转换为标准电子格式。

**不适合什么情况？**
- 处理包含大量复杂、非标准格式或严重错误信息的文本（AI可能无法准确识别）。
- 需要实时同步或管理通讯录（它只是一个生成工具，不是通讯录管理软件）。
- 处理图片文件（需要先通过其他OCR工具将图片转为文字）。

## 【二】使用方式（给第一次接触的人）

**页面输入是什么？**
- 一个大的文本框，用于粘贴包含联系人信息的文本。

**用户通常会做哪几步操作？**
1.  **粘贴文本**：将你的联系人信息（如“张三 经理 电话138... 邮箱zhang@...”）粘贴到左侧的文本框中。
2.  **点击提取**：点击下方绿色的“📇 提取联系人”按钮。
3.  **预览与选择**：在右侧区域，你会看到AI提取出的联系人卡片列表。你可以勾选需要导出的联系人。
4.  **下载文件**：点击“下载选中”或“下载全部通讯录”按钮，会得到一个 `.vcf` 文件。
5.  **导入手机**：在手机或电脑上打开下载的 `.vcf` 文件，系统通常会提示你将其导入通讯录。

**输出结果长什么样？**
- 在网页上：右侧会显示一张张美观的联系人卡片，上面有姓名、职位、电话、邮箱等信息。
- 最终文件：一个 `.vcf` 文件（本质是文本文件，包含标准格式的联系人数据）。双击它，你的通讯录应用就会自动打开并询问是否导入。

**有哪些容易忽略的使用细节？**
- **首次使用需配置API Key**：点击右上角“设置”按钮，输入你的DeepSeek API Key，否则无法使用AI提取功能。
- **可以先体验模拟数据**：如果不确定效果或没有API Key，可以点击左侧“👉 加载模拟数据预览”按钮，查看完整的工作流程和界面效果。
- **支持批量操作**：文本中可以包含多个联系人的信息，AI会尝试自动区分并批量提取。
- **灵活的选择与下载**：可以全选、单选、或任意勾选多个联系人，然后只下载选中的部分。

## 【三】核心结构拆解（学习重点）

这个网页可以清晰地分为几个功能模块：

1.  **输入与配置模块（左侧面板）**
    - **职责**：接收用户输入的原始文本，提供示例和设置入口。
    - **包含**：大文本输入框、提取按钮、示例按钮、API设置入口。
    - **逻辑**：用户在此输入信息并触发核心的“提取”动作。

2.  **AI处理引擎（隐藏的逻辑核心）**
    - **职责**：调用AI API，将非结构化的文本解析成结构化的联系人数据。
    - **逻辑**：`输入文本` + `预设Prompt` → `调用DeepSeek API` → `获得JSON格式的联系人列表`。

3.  **结果展示与管理模块（右侧主区域）**
    - **职责**：可视化展示提取出的联系人，并提供交互管理功能。
    - **包含**：
        - **状态展示区**：显示提取到的联系人总数和选中数。
        - **联系人列表**：以卡片形式展示每个联系人的详细信息。
        - **操作面板**：提供全选、下载选中、下载全部、清空等批量操作按钮。
    - **逻辑**：接收AI处理后的结构化数据，渲染成可交互的列表，并响应用户的选择和操作。

4.  **文件生成模块**
    - **职责**：将选中的结构化联系人数据，按照VCF（vCard）国际标准格式，拼接成文本字符串，并提供下载。
    - **逻辑**：`选中联系人数据` → `格式化为VCF字符串` → `创建Blob对象` → `触发浏览器下载`。

**最值得学习的设计：**
- **“模拟数据”预览机制**：在 `loadMockData` 函数中，预先定义了一组完整的模拟数据。这使得用户在不配置API Key的情况下，也能完整体验从展示、选择到下载的全部流程。这是一个**极佳的用户体验设计**，降低了初次使用的门槛，让功能演示变得直观。
- **清晰的“状态”管理**：页面通过 `x-show` 等指令，清晰地管理着“空状态”、“加载中”、“结果展示”三种界面状态，逻辑分明，用户体验流畅。

## 【四】Prompt / AI 逻辑是如何被设计的？

**Prompt 在这个页面中扮演什么角色？**
Prompt 在这里扮演了 **“数据解析器”** 的角色。它的任务不是创造新内容，而是**理解**用户输入的一段混乱文本，并从中**提取**出规整的信息。

**它解决的是“理解问题”还是“生成问题”？**
解决的是 **“理解问题”**，更准确地说是 **“信息结构化提取问题”**。AI需要理解“张三”、“138...”这些词分别代表姓名、电话，并把它们归类到正确的字段中。

**哪些信息是 Prompt 中的关键变量？**
- **系统指令（System Prompt）**：`Extract contacts from text. Return JSON: {"contacts":[{"name":"","phone":"","email":"","company":"","title":"","address":""}]}` 这是最关键的部分，它严格规定了AI的输出格式——必须是一个包含`contacts`数组的JSON对象，且每个联系人对象有固定的字段。
- **用户输入（User Content）**：`this.inputText` 这是需要被解析的原始文本，是每次请求都变化的核心变量。

**如果只改 Prompt，不改代码，会发生什么变化？**
- **改变提取字段**：例如，在Prompt的JSON结构中增加一个 `"wechat": ""` 字段，AI就会尝试从文本中提取微信号码。但网页上不会显示这个新字段，因为前端展示代码没有相应修改。
- **改变提取逻辑**：例如，将Prompt改为“提取文本中的公司和职位，并总结行业类型”，那么AI的输出将完全改变，但前端代码可能无法正确解析新的JSON结构，导致页面出错或显示异常。
- **改变输出格式**：如果不要求返回JSON，而要求返回纯文本列表，那么后端的 `JSON.parse` 就会报错，功能完全失效。

**结论**：Prompt 定义了AI的“工作说明书”，而前端代码是处理这份“工作成果”的流水线。两者必须紧密配合。

## 【五】如何模仿它，做出你自己的版本？

你可以遵循以下路径，安全地创建一个属于你自己的AI信息提取工具：

**第一步：替换核心场景与数据结构（最安全）**
- **目标**：做一个“食谱生成器”。
- **操作**：
    1.  将网页标题、描述中的“联系人”、“VCF”全部改为“食谱”、“菜谱”。
    2.  修改 `mockContacts` 模拟数据，将 `name, phone...` 换成 `dishName, ingredients, steps, cookingTime...`。
    3.  修改结果展示的模板，将显示电话、邮箱的代码块，改为显示食材、步骤。
    4.  修改 `generateVCF` 函数为 `generateRecipeCard`，输出一个纯文本或Markdown格式的菜谱。

**第二步：调整AI的Prompt和输入**
- **目标**：让AI理解新的任务。
- **操作**：
    1.  在 `extractContacts` 函数中，找到发送给AI的 `system` Prompt。
    2.  将其内容改为：`Extract recipe information from text. Return JSON: {"recipes":[{"dishName":"", "ingredients":"", "steps":"", "cookingTime":""}]}`。
    3.  将函数名和变量名从 `contacts` 改为 `recipes`，以保持代码可读性。

**第三步：改变输出和交互形式**
- **目标**：优化成品体验。
- **操作**：
    1.  将下载按钮的文本从“下载VCF”改为“导出菜谱”或“复制到剪贴板”。
    2.  将文件生成逻辑从生成 `.vcf` 改为生成 `.txt` 或 `.md` 文件。
    3.  （进阶）可以增加一个“图文并茂”的展示模式，调用另一个AI接口为菜谱生成图片。

**从哪里下手最安全？**
从 **第一步** 开始最安全。因为你只修改了静态的展示内容和模拟数据，没有触动任何与AI API交互的核心逻辑。你可以先让整个页面基于模拟数据跑通“食谱”的展示和下载流程，确保前端修改无误后，再进入第二步修改AI相关部分。

## 【六】3–5 个可直接尝试的改造方向

1.  **增加输入字段，丰富联系人信息**：
    - **操作**：在Prompt的JSON结构中和前端的联系人卡片上，增加“生日(BIRTHDAY)”、“备注(NOTE)”、“个人网站(URL)”等字段。
    - **效果**：让提取的信息更全面，生成的VCF文件内容更丰富。

2.  **更换或兼容多个AI模型/API**：
    - **操作**：在设置弹窗中，增加一个下拉选择框，让用户可以选择“DeepSeek”、“OpenAI GPT”、“通义千问”等。在 `extractContacts` 函数中，根据选择动态修改请求的URL、Headers和Body。
    - **效果**：提高工具的可用性和灵活性，用户可以使用自己已有的API Key。

3.  **优化交互：增加编辑与合并功能**：
    - **操作**：在每张联系人卡片上增加一个“编辑”按钮。点击后，可以弹出一个表单修改该联系人的信息。再增加一个“合并重复联系人”的按钮，根据姓名或电话自动识别并合并重复项。
    - **效果**：使工具从一个单纯的生成器，变成一个轻量的联系人预处理工具，实用性大增。

4.  **拆分流程，增加“预览与修正”步骤**：
    - **操作**：将流程改为两步。第一步，AI提取后，在一个类似表格的界面中展示所有提取到的信息，允许用户直接在任何单元格内修改AI可能识别错误的内容（如把“王工”错误识别为姓名）。第二步，确认无误后再生成卡片和下载。
    - **效果**：显著提高数据准确性，处理复杂、混乱文本的能力更强。

5.  **增加本地处理与隐私模式**：
    - **操作**：集成一个本地运行的轻量级AI模型（例如通过WebAssembly）。在设置中提供“使用本地模型（无需API，保护隐私）”的选项。虽然能力可能不如云端大模型，但对隐私要求高的用户是巨大吸引力。
    - **效果**：突出工具的隐私安全性，拓宽使用场景。

## 【七】这个网页不适合做什么？（边界提醒）

- **不适合作为正式的通讯录管理工具**：它没有增删改查、分组、搜索、同步云端等通讯录软件的核心功能。它只是一个**导入工具**。如果你需要管理联系人，应该使用手机自带的通讯录、Google Contacts或Outlook等专业软件。
- **不适合处理极度不规范或模糊的文本**：如果文本格式完全无规律、信息残缺不全、或者有大量无关文字，AI的提取准确率会急剧下降。它最适合处理**有一定格式线索**的文本（如包含“电话：”、“邮箱：”等关键词）。
- **不适合需要极高准确率（100%）的场合**：AI可能出错，比如把公司名误认为是人名，或漏掉一些信息。对于非常重要、不容有错的联系人录入（如重要客户），建议在导入后人工核对一遍。
- **不适合实时或自动化处理**：它是一个手动操作的网页工具。如果你需要从海量邮件或聊天记录中**自动、实时地**抓取联系人，你需要的是编写一个后端服务或使用Zapier、Make等自动化平台，而不是反复打开这个网页粘贴文本。

**总结**：这个网页是一个**精巧的“文本信息结构化”演示**。它完美展示了如何利用AI解决一个具体的、繁琐的日常问题，并通过优秀的交互设计提供流畅的用户体验。它的代码结构清晰，是学习“AI应用前端”的绝佳范例。
